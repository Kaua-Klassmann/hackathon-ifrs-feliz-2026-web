# Padrões de UX

[← índice](README.md)

Comportamento, não estética. Cada padrão define o que a tela **faz**, não só como
ela parece.

---

## Hierarquia de ações

**Uma tela tem exatamente uma ação primária.** Se há duas, ou uma delas não é
primária, ou são duas telas.

| Papel | Componente |
|---|---|
| Ação principal | `<Button>` sem `variant` — uma por tela |
| Ação secundária | `<Button variant="outline">` |
| Ação terciária, barra de ferramentas | `<Button variant="ghost">` |
| Ação destrutiva | `<Button variant="destructive">` ou `<DropdownMenuItem variant="destructive">` |
| Navegação com aparência de link | `<Button variant="link">` ou `<Link>` |

```tsx
// ✅ três secundárias e uma primária
<Button variant="outline" size="sm"><SlidersHorizontal /> Ocultar</Button>
<Button variant="outline" size="sm"><Download /> Exportar</Button>
<Button size="sm"><Plus /> Novo usuário</Button>
```

**Verificação:** conte os `<Button>` sem `variant` na tela — deve haver 1, ou 0 em
telas apenas de leitura.

## Loading

Três situações, três tratamentos:

| Situação | Tratamento |
|---|---|
| Carregamento inicial de rota | `loading.tsx` com `<Skeleton>` no formato do conteúdo final |
| Ação em andamento (submit) | Controles desabilitados + `<Spinner>` e rótulo do botão no gerúndio |
| Recarregamento de lista já visível | Manter o conteúdo e desabilitar os controles. Nunca trocar por skeleton |

```tsx
const [isRedirecting, setIsRedirecting] = useState(false);
const isPending = form.formState.isSubmitting || isRedirecting;

<Button type="submit" disabled={isPending}>
  {isPending && <Spinner aria-hidden />}
  {isPending ? "Entrando..." : "Entrar"}
</Button>
```

Regras:

- O skeleton imita o **formato** do conteúdo: três linhas de tabela viram três
  skeletons de linha, não um retângulo genérico.
- O layout não pode saltar quando o conteúdo chega — reserve a altura.
- Enquanto o envio estiver em voo, os campos do formulário também ficam
  desabilitados, não só o botão.
- Nenhuma ação fica sem feedback por mais de ~300ms.
- O spinner é **decorativo** e leva `aria-hidden`. Quem anuncia o estado é o
  rótulo no gerúndio; um `role="status"` a mais só faz o leitor de tela repetir a
  mesma informação duas vezes.

**Ação que navega continua em loading até a tela trocar.** `isSubmitting` volta a
`false` quando `router.push` é *chamado*, não quando a rota chega. Desligar o
feedback nesse ponto devolve ao usuário um formulário aparentemente pronto
enquanto a navegação ainda está em voo — e um segundo `Enter` dispara o envio de
novo. Combine `isSubmitting` com um flag de redirecionamento que, uma vez ligado,
nunca é desligado: quem o apaga é o unmount da tela.

## Estado vazio

Todo container de lista precisa de estado vazio, e os dois casos são distintos:

| Caso | Mensagem | Ação oferecida |
|---|---|---|
| Nunca teve conteúdo | "Nenhum usuário cadastrado." | Criar o primeiro |
| Filtro ou busca sem resultado | "Nenhum usuário encontrado." | Limpar o filtro |

```tsx
<TableRow>
  <TableCell colSpan={columns.length} className="h-24 text-center">
    <p className="text-muted-foreground text-sm">Nenhum usuário encontrado.</p>
  </TableCell>
</TableRow>
```

Texto em `text-muted-foreground text-sm`. Nunca deixe a área simplesmente em
branco — o usuário não distingue "vazio" de "quebrado".

## Erro

Quatro mecanismos, e a escolha não é livre:

| Onde o erro está | Mecanismo |
|---|---|
| Em um campo específico, corrigível pelo usuário | `<FieldError>` inline, abaixo do campo |
| Na operação, sem campo associado | `toast.error()` |
| Na rota inteira (401, 403, 404) | `StatusScreen` de página cheia |
| Exceção de render | `error.tsx` → `StatusScreen` com ação de retry |

**Regra de decisão:** se o erro aponta para um campo que o usuário pode corrigir,
ele é inline. Se não há nada a fazer no formulário — rede, timeout, 500 — é
toast.

**O retry do `error.tsx` usa `unstable_retry()`, não `reset()`.** O prefixo
`unstable_` é do Next, não sinal de gambiarra: é o nome da prop desde a v16.2.0 e
a doc oficial manda usar ela. `reset()` só limpa o estado do boundary e
re-renderiza os filhos **sem refazer o fetch** — como o erro típico aqui vem de
uma chamada de API no servidor, o botão falharia de novo no mesmo instante.
`unstable_retry()` dá refresh no router antes de re-renderizar.

O retry é uma ação em voo como qualquer outra e segue a regra de
[Loading](#loading): botão desabilitado, `<Spinner>` e rótulo no gerúndio. Por
isso a variante de retry do `StatusScreen` **exige** `isPending` e `pendingLabel`
no tipo — esquecer o feedback vira erro de compilação, não descuido.

Erro de credencial recusada pelo servidor é **inline no campo**, porque o usuário
está olhando para o formulário e a correção é ali. Toast para erro de credencial
obriga o usuário a associar um aviso no canto da tela ao campo que precisa mudar.

```tsx
// ✅ o backend devolve errors[] por campo → inline
if (error.errors?.length) {
  error.errors.forEach((e) => form.setError(e.field, { message: e.message }));
  return;
}
// ✅ erro sem campo → toast
toast.error(error.message);
```

## Sucesso

| Tipo de ação | Feedback |
|---|---|
| Ação que navega | `toast.success()` + navegação |
| Ação que permanece na tela | `toast.success()` + estado atualizado |
| Ação destrutiva concluída | `toast.success()` nomeando o que foi feito |

A mensagem descreve **o que aconteceu**:

```tsx
toast.success(`Bem-vindo, ${user.email}!`);   // ✅
toast.success("Usuário desativado.");          // ✅
toast.success("Sucesso!");                     // ❌
```

Sucesso silencioso é aceitável quando o resultado já é visível na tela — o item
sumiu da lista. Não empilhe toast em cima de evidência visual.

Toda ação de criação leva a algum lugar: ou navega para o recurso criado, ou
volta para a origem do fluxo. Sucesso que deixa o usuário parado na mesma tela
com o formulário limpo é um fluxo incompleto.

## Confirmação de ação destrutiva

Toda ação irreversível exige confirmação explícita, em `AlertDialog`.

1. O título nomeia a ação e o alvo: **"Desativar Olivia Rhye?"** — não "Tem certeza?"
2. O corpo diz a consequência e se é reversível.
3. O botão de confirmação repete o verbo: **"Desativar"** — não "OK".
4. Confirmar é `variant="destructive"`; cancelar é `outline`.
5. O foco inicial vai no cancelar.
6. Ação de altíssimo impacto (excluir conta ou workspace) exige digitar o nome do
   alvo para liberar o botão.

**Nunca use `window.confirm()`** — não segue tokens, não é estilizável e ignora o
tema.

## Formulário

**Estrutura:** `FieldGroup` → `Field` → `FieldLabel` + controle + `FieldError`.
Sempre os componentes de `ui/field.tsx`; nunca `<label>` solto.

**Validação:**

- Zod com `zodResolver`, schema no topo do arquivo do formulário.
- Valida no submit e revalida no change. Não valide enquanto o usuário digita
  pela primeira vez.
- Mensagem em português, específica, dizendo como corrigir:

```
✅ "A senha deve ter no mínimo 6 caracteres."
❌ "Senha inválida."
```

- Erros do servidor entram nos mesmos campos via `form.setError`, para que o
  usuário não veja dois estilos de erro diferentes para o mesmo campo.

**Layout:** controles em `h-9`. `gap-4` entre campos do `FieldGroup`; `gap-1.5`
entre label, campo e mensagem de erro.

A mensagem de erro **entra no fluxo** abaixo do campo; não se reserva altura para
ela. Reservar exigiria uma linha vazia permanente sob cada campo, e o custo disso
no ritmo vertical do formulário em repouso — que é o estado em que o usuário
passa a maior parte do tempo — é maior que o do deslocamento no instante do erro.

**Campo que não faz nada não existe.** Se um controle está na tela, ele precisa
chegar ao envio e ter efeito. Checkbox decorativo é promessa falsa ao usuário.

**Foco:** o primeiro campo do formulário leva `autoFocus`. Erro que o servidor
devolve para um campo leva o foco junto — `form.setError(name, error, {
shouldFocus: true })`. Marcar o campo em vermelho e deixar o cursor onde estava
obriga o usuário a procurar com o mouse o que ele já vai ter que corrigir.

**Campo de senha:** sempre `<PasswordInput>`, nunca `<Input type="password">`
direto. Ele acrescenta duas coisas que o input cru não tem:

- **Revelar a senha.** Regra de senha complexa sem como conferir o que foi
  digitado é a maior fonte de erro de digitação do cadastro. O botão é um
  `InputGroupButton` com `aria-label` em pt-BR e `aria-pressed`.
- **Aviso de Caps Lock**, em `aria-live="polite"`, visível só enquanto a tecla
  está ativa. É a causa mais comum de 401 legítimo, e o campo mascarado esconde
  justamente a evidência.

**Requisitos de senha** ficam em `text-muted-foreground` enquanto o usuário
digita e só passam a `text-destructive` depois do primeiro submit falho. Antes
disso, todo requisito ainda não atendido é apenas um requisito que o usuário
ainda não chegou a atender — pintar de vermelho quem acabou de começar a digitar
é acusar de erro o preenchimento normal.

## Navegação

- A sidebar marca o item ativo por `usePathname()`, com `aria-current="page"`.
- Um item de menu por rota real. Item ainda não implementado fica `disabled`:
  apagado, sem navegar e fora da ordem de foco — não some, mas também não engana.
  O estado desabilitado é o que comunica a indisponibilidade; o badge é ênfase
  opcional, `soon` para o que já está no roteiro e `new` para o que acabou de
  entrar.
- Breadcrumb entra a partir de três níveis de profundidade.
- Toda tela de status oferece exatamente um caminho de saída, e ele é a **ação
  primária** — `<Button>` sem `variant`. Não há nada mais importante na tela pra
  disputar com ele; marcá-lo como secundário afirmaria o contrário. A decisão é
  do `StatusScreen`, não de cada tela: 404, 403 e erro de render usam o mesmo
  botão de propósito.

## Densidade e ritmo vertical

| Espaço | Uso |
|---|---|
| `gap-1` / `gap-1.5` | Elementos de uma mesma linha lógica: label + campo |
| `gap-2` | Itens de barra de ferramentas, ícone + texto |
| `gap-3` | Itens de linha de tabela, controle + rótulo |
| `gap-4` | Campos de formulário, blocos de um card |
| `gap-6` / `space-y-8` | Seções de uma página |

Container de página: `p-4 md:p-6`. Header: `px-4 lg:px-6`.

**Não invente valor intermediário.** Se `gap-3` está apertado e `gap-4` largo, use
`gap-4`. Quatro pixels não justificam sair da escala.

## Responsivo

Breakpoints do Tailwind; os relevantes aqui são `sm` (640), `md` (768) e `lg`
(1024).

**Mobile-first:** escreva o estilo base para a tela pequena e adicione o
comportamento maior com prefixo.

```tsx
<div className="p-4 md:p-6" />        // ✅
<div className="p-6 max-md:p-4" />    // ❌ parte do desktop
```

- Alvo de toque com no mínimo 36px de altura — `h-9`, o padrão dos controles.
- Tabela em tela estreita: rolagem horizontal no container. Nunca encolher a
  fonte.
- A sidebar vira `Sheet` no mobile; o comportamento já vem do componente.
- Nenhum conteúdo essencial fica escondido apenas no mobile.

## Foco e teclado

**Nunca remova o anel de foco sem substituí-lo.**

```tsx
<button className="outline-none" />                                        // ❌
<button className="outline-none focus-visible:ring-3 focus-visible:ring-ring/30" /> // ✅
```

Os componentes de `ui/` já trazem `focus-visible:ring-3 focus-visible:ring-ring/30`.
Se você está removendo, provavelmente está resolvendo o problema errado.

- Toda ação alcançável por `Tab`, em ordem correspondente à leitura visual.
- `Esc` fecha dialog, sheet, dropdown e command. `Enter` submete formulário.
- Elemento interativo é `<button>` ou `<a>` — nunca `<div onClick>`.
- Ícone sem texto exige `aria-label` em português: `aria-label="Abrir ações de Olivia Rhye"`.
- Não aninhe interativos; use `render`:

```tsx
<Link><Button>Voltar</Button></Link>               // ❌ <a> dentro de <button>
<Button render={<Link href="/" />}>Voltar</Button>  // ✅
```

## Contraste mínimo

| Elemento | Mínimo |
|---|---|
| Texto normal (< 18,66px, ou não-bold) | **4,5:1** |
| Texto grande (≥ 18,66px, ou ≥ 14pt bold) | **3:1** |
| Ícone, borda de campo, indicador de estado | **3:1** |
| Anel de foco contra o fundo adjacente | **3:1** |

Os pares de token do preset já cumprem. **A obrigação de medir é de quem
introduz cor nova**, e a medição vale para os dois temas: um par pode passar no
light e falhar no dark.

## Conteúdo e voz

- Português do Brasil, tratamento por "você".
- Rótulo de botão é verbo no infinitivo: "Entrar", "Cadastrar", "Desativar" — não
  "Login", não "OK".
- Título de tela é frase curta sem ponto final; título de tela de status termina
  com ponto ("Acesso negado.").
- Mensagem de erro diz o que fazer, não o que a máquina sentiu.
- Código de erro e stack vão para `console.error`, nunca para a tela.
